# Ecosystem integration architecture

Status: implemented Axora-side foundation; NOT production_ready. Scope: Axora3/Axora only, 2026-11-11. See ECOSYSTEM_INTEGRATION_PLAN.md for inspected gaps and ECOSYSTEM_INTEGRATION_QA.md for evidence.

Axora owns customer/order links, delivery accounting, subscriptions and verified payment records. Factory owns requirement analysis, missing questions, ranking, design options, coding, QA and preview/delivery decisions. The customer dashboard owns its identity/membership and server-side Sheets adapter. Customer sites remain independent deployments. No applications are merged.

The new /admin/ecosystem console preserves the existing admin shell and adds customers, requirements, projects, templates, Factory jobs, provider observations, QA, previews, delivery, access, Sheets, subscriptions, payments and append-only audit views. Existing digital-template sales and manual one-time payment actions remain separate from the new subscription ledger. Factory answers must be reviewed against actual order answers; Axora never invents missing customer information or selects a template automatically.

Admin session + is_admin checks precede commands. A service-only transactional RPC records an idempotent command and durable task; a leased worker calls fixed authenticated remote endpoints. Receipts must match the linked order, site and customer. Only the Factory's actual delivered project receipt starts the immutable 30-day trial. A preview/build does not. Site/Sheets preparation can happen before generation with no dashboard customer access; access provisioning is queued only after confirmed delivery. An active access receipt requires verified identity, matching customer email and dashboard user ID; invited/pending is displayed honestly.

Credentials remain server-only. Browser summaries omit private spreadsheet mappings. Spreadsheet IDs from clients are never accepted. Mappings are site-bound, unique and cannot silently change. Sheets content CRUD and revalidation stay in the separate dashboard/site adapter; this task does not pretend that absent dashboard APIs work. Public published reads and validated create-only visitor submissions remain responsibilities of those independent applications.

Subscription plans are fixed at 20,000 MNT monthly and 228,000 MNT annually (5% below 240,000). Early payment preserves remaining trial days. Provider verification binds merchant, payment ID, invoice, amount, currency and timestamp. Duplicate payments/events cannot extend coverage twice. Cancellation takes effect at period end; renewal uses another verified invoice. Suspension is configurable and defaults off; desired write suspension is distinguished from a confirmed remote policy receipt. There is no website/data deletion path. Automatic charging, refunds, chargebacks and provider reconciliation are not completed integrations.

Tasks use 120-second fenced leases, at most five attempts and bounded network requests. Retryable failures back off; missing contracts/configuration block visibly. An administrator may retry within the cap. Factory polling is queued no more than once per minute and dashboard health checks every five minutes. One tick processes one task, so schedule capacity and monitoring must match volume. Requirements versions fence stale work; uncertain remote intake must be reconciled with the original idempotency key. External services must implement durable idempotency too.

Production dependencies: staged migration; actual Factory deployment and tokens; dashboard provisioning/health/access/policy API implementation in a separately authorized task; a real payment bridge/provider; authenticated staging customers and complete cross-application acceptance tests. Bounded admin summaries currently show at most 100 rows; large installations need pagination/operational monitoring before rollout.
